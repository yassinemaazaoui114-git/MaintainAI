# MaintainAI — living spec

Personal learning / portfolio project: a small CMMS (machines, component replacements, failures) with a
predictive-maintenance risk score learned from recorded failures, explanations and a what-if tool, plus
benchmarks on public predictive-maintenance datasets.
This file is the source of truth for scope, decisions and open questions. Update it with every change.

_Last updated: 2026-10-28_

## 2. Confirmed vs. assumed

**Confirmed (by the owner)**
- Personal learning project for a CV. No academic scope limits, no report.
- Stack: Python, pandas, scikit-learn, Streamlit, SQLite.
- App data = Microsoft Azure Predictive Maintenance sample dataset (Kaggle mirror:
  https://www.kaggle.com/datasets/arnabbiswas1/microsoft-azure-predictive-maintenance). License not clearly
  stated; the owner decided to use it as a **non-commercial, educational demo** on these conditions: raw CSVs
  never committed (`data/azure_pdm/` git-ignored), only a small daily-aggregate SQLite DB committed, README
  credits Microsoft with the link, states the license is unclear, says a real deployment would load its own
  data, and that the demo data will be removed on request.
- It is a public dataset generated by Microsoft; its failure events were not designed by this project. Say so.
- Benchmarks use AI4I 2020 and C-MAPSS FD001, both simulated public datasets, and are labelled as such.
- Hosting: Streamlit Community Cloud; the owner pushes and deploys.
- No push without the owner's OK.

**Assumed (working assumptions — change freely)**
- Horizon 7 days; label = any component failure in (d, d + 7].
- Thresholds: Critical ≥ 50 (more likely than not), Warning ≥ 20 (see D27). Stored in `risk_model.pkl`.
- "Now" for the app = the latest record date, 2015-12-31 (see D2). Form dates default to it and cannot go past it.
- A machine added through the form has no history: its components count as old as the machine, its sensor
  values as that day's fleet median.
- On Streamlit Cloud, records added through the forms are temporary (the container's disk resets on restart). Fine for a demo.

## 3. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | One feature module (`risk_features.py`) used by training, notebook and app | Training and scoring can't drift apart |
| D2 | Features are computed in Python "as of" the latest record date, not the wall clock | The demo data is frozen (2015); measured against today every component would look years overdue |
| D9 | All HTML embeds size their own iframe (`height="content"` + fit script) | Python-side height estimates clipped the taller embeds |
| D10 | Risk status is judged on the rounded, displayed score | A displayed "40" was labelled Normal |
| D11 | Saving a replacement or failure also reloads machine features | Otherwise the risk score didn't update until a page refresh |
| D12 | Live features include every machine, even one without records | Adding a machine crashed the dashboard (NaN features) |
| D13 | Sidebar nav radio has a fixed `key` | Its labels contain record counts; a count change reset the page to Dashboard |
| D14 | Form success messages survive `st.rerun()` via session state | They were drawn and then wiped by the rerun |
| D16 | Benchmarks: model choice by training-CV only; test set touched once | Avoid leakage and test-set selection bias |
| D17 | Raw datasets live in git-ignored `data/`; only metrics, figures and the small app DB are committed | Repo size; dataset hosting/licensing |
| D18 | `.streamlit/config.toml`: light theme base, viewer toolbar | The custom styling assumes a light base |
| D35 | `[theme.sidebar]` sets `primaryColor` and `textColor` to the colours `theme_css.py` already forces | Left unset, Streamlit's front end logged "Invalid color passed … theme.sidebar" twice per rerun; no visual change |
| D19 | `requirements.txt` = app runtime only (exact pins); `requirements-dev.txt` adds tests, notebooks, Playwright | Smaller, faster Community Cloud install |
| D20 | DB keeps **daily means** of the four sensors, not hourly readings or daily std/max | 3.8 MB instead of ~80 MB of CSV. A prototype showed daily standard deviations and 3-day means did not raise validation PR-AUC (0.630 and 0.645 vs 0.654 without them) |
| D21 | Schema: `Machines(machine_id, model, age_years)`, `Maintenance_Log(component, type, note)`, `Failure_Log(component, note)`, `Error_Log(error_code)`, `Sensor_Readings(date, volt, rotate, pressure, vibration)`; IDs `MCH-001..100`; records after 2015-12-31 dropped | Matches the source; the first hours of 2016-01-01 are not a full day |
| D22 | A replacement on the same day as a failure of that component on that machine is typed "Corrective" (743 of 3,279) | Lets the log filter scheduled vs. failure-driven work; 18 failures have no same-day replacement in the source |
| D23 | Features (15): days since each comp replaced, latest-day and 7-day mean of each sensor, errors in 7 days, age, model number | Prototype: latest-day readings added most (val PR-AUC 0.46 → 0.64); error types separately added ~0.01, not worth 4 more columns |
| D24 | Time-based split: train ≤ 2015-08-24, validation Sep–Oct, test 2015-11-01..12-24, with a 7-day purge before each boundary | Labels look 7 days ahead; a random split would leak neighbouring days of the same machine |
| D25 | Model choice on validation PR-AUC across baseline / logistic regression / Random Forest grid / gradient boosting grid; test used once, by models refit on train + val | No test-set selection |
| D26 | Random Forest with **100 trees** (not 300) | Same validation PR-AUC (0.632 vs 0.637) but exact SHAP for the fleet in ~1.6 s instead of ~9–13 s; model file 3 MB |
| D27 | Thresholds: Critical = 50 (more likely than not); Warning = highest multiple of 5 below Critical with ≥ 80% validation recall (→ 20) | Interpretable rules fixed before looking at test; Critical precision 0.74 on validation, Warning catches 80% of pre-failure days |
| D28 | No calibration step | Validation ECE 0.022 < 0.05 limit set in advance; isotonic only moved test Brier 0.0725 → 0.0719; raw forest keeps SHAP exact and additive in % points |
| D29 | Report alerts per failure event (alert on any of the 7 days before) **and** lead time, besides row-level precision/recall | "Caught" alone hides that the median Critical warning is ~2 days |
| D30 | SHAP rows cached per model input (`st.cache_resource` dict) | A saved record changes one machine; only that row is recomputed |
| D31 | What-if changes only model inputs (days since replacement → 0, sensors → fleet median, errors → 0), compares against the fleet's medians, writes nothing | Honest, reversible simulation; the page says it is not a guarantee |
| D32 | Dashboard row "Failures per month | Explain a machine": chart frame stretched by CSS to the explanation column's height at ≥ 640 px, natural heights when Streamlit stacks the columns | Equal heights without guessing pixel heights in Python |
| D33 | Health table and log tables show N rows, then scroll under a sticky header; max-height measured in the iframe from real row heights; driver text on one line with ellipsis + tooltip | 6 visible rows exactly, whatever the fonts; log tables render the latest 500 rows (filter for older) |
| D34 | Model page is layered: plain words and four headline numbers first, details in expanders, benchmarks in a collapsed expander | Recruiters and users get the answer first; reviewers can drill down |

Retired 2026-10-28 with the synthetic data: D3–D8 (12-month windows, weekly snapshots, machine-level split,
Random Forest regressor on a proxy formula) and D15 (old explanation layout). The proxy formula and the synthetic
`factory_maintenance.db` are deleted.

## 4. Open questions

- The median Critical warning is ~2 days. A longer horizon (14/30 days) or features that capture slower wear might
  give more lead time; worth trying as a second score?
- `days_since_comp*` dominate global SHAP. Some of that may be the generator's design (components replaced on a
  schedule). Check partial dependence before reading it as a physical effect.
- Gradient boosting ties the forest on test. Tune it more, or keep the forest for its probability-scale SHAP?
- Persistent storage for the hosted demo, or keep it ephemeral?

## 5. Results snapshot

Risk model, test months 2015-11-01..12-24 (5,400 machine-days, 12.6% positive) — `results/risk_model/metrics.json`:

| Model | PR-AUC val | PR-AUC test | ROC-AUC test | Brier test |
|---|---|---|---|---|
| Baseline (failure rate) | 0.125 | 0.126 | 0.500 | 0.110 |
| Logistic regression | 0.293 | 0.293 | 0.689 | 0.102 |
| **Random Forest** (selected) | 0.633 | 0.630 | 0.909 | 0.072 |
| Gradient boosting | 0.614 | 0.628 | 0.913 | 0.071 |

Alerts on test (Random Forest): Critical ≥ 50 → 303 machine-days flagged, 78 false alarms (precision 0.74,
recall 0.33); 100 of 111 failure events had a Critical alert in the 7 days before, 93 at least 2 days ahead,
median lead 2 days. Warning ≥ 20 → 108 of 111, median lead 7 days, precision 0.39.
Fleet on 2015-12-31: 76 Normal, 14 Warning, 10 Critical.
